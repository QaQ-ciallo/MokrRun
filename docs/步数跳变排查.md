# 步数跳变排查（2026-11-17）

用户现象：前约三分钟步数正常增长，之后突然到五万多步。

## 结论与证据边界

源码存在确定的双源计步缺陷，足以造成上述数量级的跳变：

- `SensorHook.RegHook` 记录监听器供 `pushStep` 直接调用，同时默认仍允许系统注册硬件计步。
- `MotionEngine.sSuppressRealSteps` 原默认值为 `false`；`ConfigSync.buildLine` 没有下发 `rs=1`。
- 硬件 `TYPE_STEP_COUNTER` 的 `values[0]` 是开机以来传感器启用期间的累计步数，而合成值来自模块自己的累计计数。这两套基数不能混用。
- 原 `rs=1` 分支给返回 `boolean` 的 `registerListener` 设置 `null`，不能正确表达注册成功。
- 原系统队列 hook 仅计数日志，没有过滤任何事件，也没记录原始计步值。

因此，若合成流增长到几百步后收到硬件累计值 50000，应用可观察到突变。这里是基于源码的因果推断；本次没有捕获用户发生异常时的事件，不能认定已经实机证明。读取设备日志时，缓冲区仅剩空闲与其他传感器统计；`dumpsys sensorservice` 将计步值显示为 `[value masked]`。约三分钟这一时刻没有证据表明是固定硬件延迟，可能与重新注册、应用生命周期或事件投递有关，仍待复现。

Android 官方语义：<https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion>

## 修复

1. 进程内默认 `sSuppressRealSteps=true`，防止配置到达前就混入真实计步；正常下发配置显式带 `rs=1`。
2. 拦截计步注册时返回 `Boolean.TRUE`，让应用正常使用模块维护的合成监听器。
3. 在系统 `dispatchSensorEvent` 入口按 handle 对应的 Sensor 类型过滤真实 counter/detector，覆盖先前注册和排队中的事件，其他传感器放行。
4. 合成事件直接调用监听器，不经过系统队列，因此继续正常投递。`rs=0` 保留为双源诊断选项。

队列类型判断使用系统 `mManager.mHandleToSensor` 映射；不能读取尚未首次分发的 `SensorEvent.sensor`，该字段此时可能为空。相关系统实现：<https://android.googlesource.com/platform/frameworks/base/+/refs/heads/master/core/java/android/hardware/SystemSensorManager.java>

默认屏蔽覆盖目标进程整个生命周期（包括暂停/尚未开始），以确保不会切换计步基数；需要真实计步时应关闭模块或明确使用诊断配置。

完整构建与 APK 签名验证通过，版本为 1.0.116，产物 `build/MokrRun.apk`。
