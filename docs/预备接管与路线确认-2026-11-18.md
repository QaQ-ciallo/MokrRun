## 2. 状态转移表

`MotionEngine` 状态值（`mode()` 可读，`ConfigSync.MODE_*` 同值）：

| 状态 | 值 | 坐标来源 | 路线推进 | 模拟步数 | 进入方式 |
|---|---|---|---|---|---|
| OFF | 0 | 真实位置 | 否 | 不累加 | 未启用 / `endSession()` / `setMode(0)` |
| RUNNING | 1 | 已确认路线 | 是 | 累加 | `applyConfirm()` 成功 |
| PAUSED | 2 | 冻结的模拟位置 | 否 | 不累加 | `setMode(2)` / 人脸冻结 |
| PREPARED | 3 | 最新真实位置 | 否 | 不累加 | `prepareSession()` |

转移表（行=当前，列=操作）：

| 当前 \ 操作 | prepareSession | applyConfirm(同会话/新token) | applyConfirm(旧token) | applyConfirm(旧会话/已结束) | setMode(2) | setMode(1) | endSession / setMode(0) |
|---|---|---|---|---|---|---|---|
| OFF | → PREPARED | 拒绝（会话未启用） | 拒绝 | 拒绝 | 不接管（无确认路线） | 不接管（无确认路线） | 保持 OFF |
| PREPARED | → PREPARED（刷新会话，清确认） | → RUNNING（建路线+重置基数+建时钟） | 拒绝（幂等） | 拒绝 | → PAUSED（仍不接管：无确认路线） | → RUNNING（无确认路线 → 仍不接管） | → OFF |
| RUNNING | → PREPARED（清确认、停止推进） | 拒绝（旧 token） | 拒绝 | 拒绝 | → PAUSED | — | → OFF |
| PAUSED | → PREPARED | 拒绝（旧 token） | 拒绝 | 拒绝 | — | → RUNNING（沿用已确认路线） | → OFF |

三个判断（逐点审计，不做全局替换）：

| 判断 | 语义 | 使用点 |
|---|---|---|
| `isSessionEnabled()` | 会话是否启用（允许无路线） | 入口层（模块 App / 回执） |
| `shouldOverridePosition()` | 仅「已确认路线的 RUNNING/PAUSED」覆盖坐标 | `LocationProbe`（6 处守卫）、`SDKLocationHook`（2 处）、`GnssHook`（1 处）、`isActive()` 兼容别名 |
| `shouldAdvanceMotion()` | 仅「已确认路线的 RUNNING」推进 | `MotionEngine.tick()`、`speedNow()`、`isRunningNow()` 兼容别名 |

各 hook 在 PREPARED 的策略（要求 §3 的对应项）：

| 组件 | OFF | PREPARED | RUNNING | PAUSED |
|---|---|---|---|---|
| `LocationProbe` | 放行真实 | **放行真实**（注册、单次、系统回调都不拦） | 拦截真实、改用合成 | 拦截真实、返回冻结点 |
| `SDKLocationHook` | 返回真实 getter | **返回真实 getter**（不返回残留 `sCurLat/sCurLon`） | 返回合成坐标 | 返回冻结坐标 |
| `GnssHook` | 不推送 | **不推送**（真实 GNSS 原样给应用） | 按 `sat` 推送 | 不推送 |
| `SensorHook` | 只注册捕获 | **模拟累计值不增长**（无 tick，故无推送） | 推送合成步 | 不推送 |
| `MotionEngine` | 不 tick 推进 | 不推进、不补算停留时长 | 推进 | 冻结 |

> 说明：`sRouteConfirmed` 只有在确认操作里置真；`prepareSession()` 会把它清掉，
> 因此「上一场的路线」不会在新会话里被当成已确认路线。

## 3. 确认协议（幂等 + 回执 + 超时）

一次确认携带：`session`、`token`、`cfg`、`origin`、`route`。

1. `MotionEngine.applyConfirm()` 校验：token 非空且未用过、会话已启用且匹配、
   起点与途经点有限且在范围内、至少 1 个途经点。任何一项失败返回中文原因。
2. 通过后**同一操作内**：写路线数组 → `resetCounters()`（里程归零、`sStepBase += sSteps`
   保持单调、`sLastTick = 0`）→ `mode = RUNNING` → 记录 `appliedToken`。
   不分成「先改起点、再改路线、最后改状态」三次更新。
3. 成功/失败都会记日志；成功额外发 `com.mokrun.app.ACK`（带 session/token/mode）。
4. 模块侧 `DraftActivity` 收到匹配 token 的 ACK 才把界面切成「运行中」并回到体适能；
   9 s 无回执 → 显示「目标进程没有回执（超时）」，不假装运行。
5. 幂等：同一 token 第二次确认返回「该路线已确认过（重复点击已忽略）」；
   结束后、会话不匹配、token 为空的确认一律拒绝。

## 4. 首页「定位当前位置」

- `home.html`：`routeOrigin` / `currentLocation` / 视野三份状态分离；`setData(..., center)`
  只在首次进入居中；定位按钮调 `Native.locateCurrent()`，收到结果才
  `map.setView([lat, lon], 17)` 并画精度圈；状态条显示「正在定位 / 先显示 N 秒前的位置 /
  已更新 / 失败原因」。
- `LocationHelper`：`cachedWithAge()`、`locationEnabled()`、`requestFresh()`；
  权限缺失、定位关闭、12 s 超时、无结果都有明确回调。
- `LocateTracker`：单飞（进行中重复点击忽略）、超时必结束、缓存只做预览（≤60 s）。
- 定位结果只更新当前位置，不写 `Store.origin`，不改已画路线；GCJ-02 只转一次。

## 5. 起点连续性规则与依据

`RouteDraft.check()`：

| 规则 | 取值 | 依据 |
|---|---|---|
| 定位新鲜度 | ≤ 30 s（`MAX_FIX_AGE_MS`） | 与「确认要拿新鲜定位」一致；更旧的值不足以判断连续性 |
| 容差 | `max(50 m, 3 × accuracy)` | 50 m 覆盖室内网络定位 20~30 m 精度下的步行误差；3 倍精度让弱信号自动放宽 |
| 精度差提示 | accuracy > 35 m | 只提示不阻断 |
| 超出容差 | 第一次阻断并要求二次确认，第二次按下同一按钮明确「仍使用该起点」 | 不静默改用户起点、不生成过渡轨迹 |

**没有**写死「必然通过应用检测」的阈值；这是模块自己的产品容差，
实机效果需要按 §9 验证。

| P2 | 旧控制入口绕过确认 | `applyFromIntent()` 无条件 `sRouteConfirmed = hasRoute()` | 只有 CONFIRM 或旧协议 `run=1`（开始）能授予确认；未确认会话里的旧式暂停被忽略；带 session 的迟到命令在接收器层按 `sessionId` 拒绝；旧协议范围=不带 session 的 mode 命令 |
| P2 | 启用阶段把发送成功当接收成功 | `sendPrepare` 只要不抛异常就返回 true，无 PREPARE 回执 | 引擎在 `prepareSession()` 发 `op=prepare` 回执；模块侧新增 `EnableFlow`（SENT→ACKED/FAILED）按 session 匹配 + 6 s 超时；未回执不写 `runMode=3`；导航结果单独记录，失败提示「已启用，但打开体适能失败」 |

| 操作 \ 状态 | OFF | PREPARED | RUNNING | PAUSED |

### 14.3 结论与建议

- 第 1 项（定位）通过；第 2 项的「不谎报」要求通过、**「收到回执才显示已启用」未通过**；
  第 3–5 项因阻塞未执行 → **本轮验收不通过，不进入发布收尾**。
- 下一轮需要换回执通道设计，可选：
  1) 模块 App 侧轮询：目标进程把结果写进**它自己**的外部目录，模块 App 用
     `MANAGE_EXTERNAL_STORAGE` 读取（需权限，改动大）；
  2) 目标进程 `startActivity` 到模块 App 的透明 Activity 携带回执（会抢前台，需产品确认）；
  3) 由用户确认：模块 App 显示「已发送，请在体适能确认已启用」并允许手动标记，
     不改自动化语义但放弃强回执。
- GPS 异常与人脸掉登录：本轮按要求未排查，不作为阻塞项。
