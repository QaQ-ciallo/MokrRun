# PREPARE/CONFIRM 回执通道：三种方案对比（2026-11-19）

背景：实机 1.0.135–1.0.141 复现——引擎已 `ack sent op=prepare`，但模块 App 收不到。
系统侧证据：

```text
Pending broadcast #0: Intent { act=com.mokrun.app.ACK pkg=com.mokrun.app cmp=.AckReceiver }
W/ContentProviderHelper: No provider info for content provider com.mokrun.app.config
        when providerRunning is false, caller=...com.bxkj.student...
adb shell content query --uri content://com.mokrun.app.config/config   # shell 可读
```

结论：模块 App 一退到后台，MIUI 就拒绝别的应用访问它的 Provider，并把指向它的广播排进队列。
所以「目标进程 → 模块 App」这条回边在当前设备上不可用，需要换通道。

评估维度：改动量（代码/清单/权限）、风险（语义、风控、审核、可验证性）、估时、对现有测试的影响。

---

## 方案 A：模块侧轮询（目标写外部目录，模块读）

**通道**：目标进程写 `…/Android/data/com.bxkj.student/files/mokr_ack.json`（它自己的目录，无需权限）；
模块 App 每 500 ms 读同一路径。

| 项 | 内容 |
|---|---|
| 改动 | 引擎 `sendAck` 加一条落盘分支（~40 行）；模块新增 `AckPoller`（Handler 轮询 + 文件解析，~70 行）；`AndroidManifest` 加 `MANAGE_EXTERNAL_STORAGE`；设置页/首页加权限引导（~50 行 + 文案）|
| 改动量 | 中：约 160 行 + 权限引导 UI + 清单 |
| 风险 | ⚠️ **最高**：`MANAGE_EXTERNAL_STORAGE` 是「所有文件访问」，需用户到系统设置手动开；应用商店/用户观感差；MIUI 对后台读 `/sdcard` 一般放行但不保证；多用户/工作资料下路径不同 |
| 语义 | 强：模块拿到的是目标进程真实写入的结果，等价于现在的回执 |
| 可验证 | 好：`adb shell cat` 同路径即可断言；JVM 只测 JSON 解析，通道需实机 |
| 估时 | 0.5–1 天（含权限引导与实机验证） |

---

## 方案 B：透明 Activity 回执（目标 startActivity 到模块的转发页）

**通道**：引擎发完广播后（失败或超时）`startActivity` 到模块的 `AckRelayActivity`（透明、`NO_ANIMATION`），
extras 携带 op/session/token/ok；该页 `onCreate` 里把 extras 交给 `AckReceiver.deliver()` 后立刻 `finish()`。

| 项 | 内容 |
|---|---|
| 改动 | 模块新增 `AckRelayActivity`（~35 行）+ 清单注册（exported + 自定义权限保护）；引擎加一次 fallback `startActivity`（~25 行） |
| 改动量 | 小：约 60 行 |
| 风险 | ⚠️ **中高**：① 会抢前台（体适能瞬间失焦再回来），可能触发目标应用的前后台/人脸风控（本项目已见过人脸流程敏感）；② MIUI「后台弹出界面」默认关闭，可能直接被拦；③ exported 组件暴露面（需 `signature` 级自定义权限兜住） |
| 语义 | 强：拿到的是目标进程主动投递的结果 |
| 可验证 | 一般：JVM 测不到；实机要连带观察「是否影响跑步/人脸」 |
| 估时 | 0.5 天 + 实机回归（含风控观察） |

---

## 方案 C：弱确认（放弃强回执，明确「已发送未确认」）

**通道**：不回执。`EnableFlow` 增加 `SENT_UNCONFIRMED`；界面显示「已发送，请在体适能里确认已启用」，
并提供手动「标记为已启用」；超时只提示「未确认」，不改任何状态。

| 项 | 内容 |
|---|---|
| 改动 | `EnableFlow` 加状态（~15 行）；首页/悬浮窗文案与手动标记（~35 行） |
| 改动量 | 小：约 50 行，无新权限、无新组件 |
| 风险 | ✅ 技术风险最低；但**语义最弱**：无法证明引擎真在 PREPARED，用户误判可能照跑；虽然仍不谎报「已启用」，但「已启用」这件事变成用户口头确认 |
| 语义 | 弱 |
| 可验证 | 好：JVM 可测状态机；实机一眼可见 |
| 估时 | 0.25–0.5 天 |

---

## 汇总

| 维度 | A 轮询 | B 透明页 | C 弱确认 |
|---|---|---|---|
| 代码量 | ~160 行 + 权限 UI | ~60 行 | ~50 行 |
| 新权限 | `MANAGE_EXTERNAL_STORAGE`（重） | 无（新增 exported 组件） | 无 |
| 抢前台 | 否 | **是**（一次） | 否 |
| 语义强度 | 强 | 强 | 弱 |
| 被 MIUI 拦的概率 | 低（读自身可见路径） | 中（后台拉起 Activity 受限） | 不适用 |
| 对现有测试影响 | 新增 poller 单测 | 无（通道在 Activity 层） | 改 EnableFlow 状态机测试 |
| 估时 | 0.5–1 天 | 0.5 天 + 实机回归 | 0.25–0.5 天 |

## 建议

1. 若产品坚持「必须证明已启用」且能接受**一次前台切换** → **B**（改动最小，语义不打折），
   但必须同时验证：切换前台是否触发体适能的人脸/风控提示；MIUI 后台拉起是否被拦。
2. 若要**零打扰**且可接受一个重权限 → **A**；权限引导要写清楚用途，否则用户不会开。
3. 若本轮只求「不谎报、能交付」→ **C**，并在发布说明里明确「启用状态需用户确认」。

不建议把 A+B 一起做：两条通道都要实机验证，回归成本翻倍，收益只是互为兜底。
若担心 B 被 MIUI 拦，可以先做 B，用 30 分钟实机确认「后台拉起是否成功」，失败再转 A。

另有一条未列入三选一的路径：设备已有 root（SukiSU），模块侧可用 `libsu` 请求 root 直接读目标私有目录，
语义强、不抢前台、不需重权限；但引入 root 依赖，且本项目一直避免在模块 App 侧要 root，故单列备注。
