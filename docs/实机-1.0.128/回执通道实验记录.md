## E2：核对 Provider 在别的身份下是否可用

```text

→ Row: 0 speed=4.8, cadence=3.12, stride=1.54, anti=1, origin=, route=, run=0
```

事实：**shell 身份可读**。这只说明「两条调用路径结果不同」，不能据此推断原因
（shell 有额外权限，且 query 与 call 是两条不同的解析/授权路径）。

因此「MIUI 后台限制」不是充分解释，之前那条推断作废。

## 当前可确认与不可确认

可确认：
1. 目标进程发起的 `ContentProvider.call()` 在当前设备上**从应用身份**不可用（前台/后台都一样）；
2. 发往模块 App 的广播在同一次操作中没有到达（处于 Pending 或未投递，两者都观察到过）；
3. 目标进程**读**该 Provider 是正常的（引擎每 tick 读 run/cfg 成功）；
4. shell 身份 `query` 正常。

不可确认（不要再当结论用）：
- 究竟是 MIUI 的 provider 白名单、`call()` 的启动语义，还是广播冻结策略；
- 换一台非 MIUI 设备是否同样失败；
- 目标应用进程内的 Xposed 注入是否影响 ContentResolver 的调用身份。

## E4（下一轮，最小验证）：ResultReceiver / Binder 回调

设计：模块启动目标时把 `ResultReceiver`（Parcelable，跨进程 binder）放进 Intent extras；
目标在 `prepareSession()` / `applyConfirm()` 完成后直接 `rr.send(mode, bundle)`。
回调是**模块 → 目标方向**传递的 binder，目标调用它不需要访问模块的 Provider、不需要广播、
也不抢前台。

需要验证的三点：
1. 冷启动路径（Intent 带 ResultReceiver）能否拿到回调；
2. 目标已在运行时（CMD 广播带 ResultReceiver）能否拿到回调；
3. 回调是否受 MIUI 对「跨进程 binder 调用」的额外限制。
