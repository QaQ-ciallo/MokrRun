# 模块代码审计（2026-11-18）

## 结论与范围

针对本地 1.0.116 工作树（含上一轮尚未提交的计步补丁），确认 **14 类问题**，对应 **17 个失败场景**。三个对照场景通过：有效路线解析、正常 tick 推进、暂停 tick 不推进。

本轮只新增复现测试与审计文档，没有修改生产源码、安装 APK、操作手机界面或启动跑步。这里的“确认”指实际生产 Java 方法在指定输入/状态下违反可检验的行为约束，**不代表确认了此前手机上五万步异常的唯一原因**。

主要测试对象：`MotionEngine`、`SensorHook`、`IntentBridge`、`LocationProbe`、`GnssHook`、`ResourceProbe`。同时阅读了配置存储、广播控制、悬浮窗、地图保存、设置页面、模块安装入口及构建脚本；不能把这次审计理解为证明未列出的代码完全没有 bug。

## 已确认的问题

### 1. P1：步频溢出为 Infinity，tick 无限循环

- 位置：`MotionEngine.java:367`、`:504`、`:505`；设置入口 `SettingsActivity.java:84`、`:89`、`:96`。
- 输入：`cadence=99999999999999999999999999999999999999999999999999`。
- 实际：`Float.parseFloat` 返回正无穷，`cadence > 0.1f` 允许写入。随后 `sStepAccum` 变成正无穷，减 1 后仍为正无穷，`while (sStepAccum >= 1.0)` 永远无法结束。
- 复现：`cadence_infinity` 确认配置被接受；`cadence_infinity_tick` 运行实际 tick，200ms 后仍未返回，观察到约 890 万步。该危险循环仅在隔离的 JVM 守护线程中执行，进程结束后退出。
- 正常应用引擎在主线程 Handler 执行 tick，此输入会阻塞该线程。设置页也只排除 `v <= 0`，没有排除溢出和限制步频；因此输入可由模块设置传播到引擎。
- 修复方向：所有数值入口校验有限值及业务范围；每 tick 的补步循环也应有明确上限。
- 与原问题的关系：这是确定可产生巨量步数的另一条路径，但没有证据表明用户原场次使用过该输入，不能将二者直接等同。

### 2. P1：冻结期间的“结束”被旧状态覆盖；未开始也能被恢复为运行

- 位置：`MotionEngine.java:126`、`:147`、`:150`、`:189`。
- 场景 A：运行 → `freezeForFace()` → `setMode(0)` → `resumeAfterFace()`。
- 实际：结束后 `sFaceFrozen` 未清除，恢复直接把旧 `sPrevMode=1` 写回，结果 `mode=1`。
- 场景 B：原本 `mode=0` → 冻结 → 恢复。
- 实际：`sPrevMode == 0 ? 1 : sPrevMode` 明确把停止态改为运行态。
- 复现：`stop_during_freeze`、`freeze_while_stopped` 均失败，实际输出 `mode=1`。
- 修复方向：停止操作取消冻结与恢复任务；恢复只能恢复仍有效的原状态，不得把 0 转为 1。

### 3. P1：Provider 可访问时覆盖显式暂停和内部冻结

- 位置：`MotionEngine.java:174`、`:179`、`:277`。
- 输入状态：Provider 中 `run=1`，引擎执行显式 `setMode(2)`。
- 实际：超过模式缓存窗口后，`readMode()` 先调用 `readProvider()`；后者无条件 `sMode=run`。`sIntentMode` 只在 Provider 读取失败时才被检查，因此显式暂停变回运行。
- 复现：`provider_overwrites_pause` 用可访问的配置行与过期缓存调用真实读取路径，最终 `mode=1`。
- 影响条件：Provider 可访问、其保存状态与引擎命令/内部冻结不一致。内部冻结本身没有把暂停写回模块 prefs，能形成此条件。悬浮窗正常暂停若已同时把 prefs 写为 2，则不属于这个复现前提。
- 修复方向：明确配置值与临时运行状态的优先级；不能让配置轮询撤销内部冻结或更新的显式命令。

### 4. P1：onNewIntent 读取旧 Intent，忽略新配置

- 位置：`IntentBridge.java:42`、`:44`、`:56`。
- 场景：Activity 持有原启动 Intent，新配置由 `onNewIntent(newIntent)` 到达，Activity 自身未调用 `setIntent(newIntent)`。
- 实际：hook 丢弃 `param.args`，转而读取 `Activity.getIntent()`，拿到旧 Intent。测试中新的 `run=1;speed=3.5` 未生效，仍是 `mode=0;speed=4.8`。
- 复现：`new_intent`。
- 框架依据：Android 官方明确说明 `onNewIntent` 中 `getIntent()` 仍返回旧 Intent，除非调用 `setIntent`。该问题有条件边界，不宣称目标应用所有 Activity 都没有自行调用 `setIntent`。
- 修复方向：在新 Intent hook 中直接读取回调参数，onCreate 再读取 Activity 启动 Intent。

### 5. P1：开放路线到末端后，直接跳回第一段

- 位置：`MotionEngine.java:497`、`:498`、`:499`。
- 场景：合法三点路线，最后一点没有连回起点；让引擎处于末段终点前 0.2 米，推进约 250ms。
- 实际：代码将 `sSeg=0`、`sSegProgress=0`，不经过末点到起点的路程，直接在第一段重新插值。
- 复现：`route_wrap_jump`；一次 tick 的位置移动约 **146.97 米**，引擎累计约 **1.20 米**。
- 该路线可由现有地图保存流程产生：地图允许保存任意途经点，没有强制末点回到起点。
- 修复方向：明确路线末端语义，选择停止、沿原路返回或沿明确的闭合路段前进；同时保留跨段剩余距离。

### 6. P2：清空路线只更新缓存标识，没有清除旧坐标数组

- 位置：`MotionEngine.java:379`、`:406`。
- 场景：先加载有效路线，再下发 `origin="";route="[]"`。
- 实际：`sLastOrigin`、`sLastRouteHash` 已更新，但随后提前 return；`sLat/sLon` 仍保留旧路线，`hasRoute()` 继续为 true。
- 复现：`clear_route`；清空后仍有 3 个旧点。
- 修复方向：空路线应清空有效路线状态，不能只改变用于去重的配置标识。

### 7. P2：传感器部分注销错误地移除整个计步监听器

- 位置：`SensorHook.java:153`、`:158`。
- 场景 A：listener 注册 counter；应用调用 `unregisterListener(listener, accelerometer)`。
- 实际：hook 没检查传感器参数，直接把 listener 从计步表删除。后续计步事件丢失。
- 场景 B：同一 listener 注册 counter 和 detector，仅注销 counter。
- 实际：仍有效的 detector 也不再接收合成事件，因为表只记录一个类型，注销直接删整个 listener。
- 复现：`unregister_other_sensor`、`unregister_one_step_type`。
- 修复方向：记录 listener 的有效传感器注册集合；有指定 Sensor 时仅移除对应注册，未指定时才全部注销。

### 8. P2：定位监听器注销后仍被引擎持有并继续回调

- 位置：`MotionEngine.java:245`、`:523`；`LocationProbe.java:24` 起的安装与注册路径。
- 场景：通过四参数 `requestLocationUpdates` hook 捕获 listener，然后框架执行 `removeUpdates(listener)`。
- 实际：模块没有对应的移除 hook，也没有从 `MotionEngine.sListeners` 删除的路径；下一次 tick 仍回调该 listener。
- 复现：`location_unregister`；先确认注册成功并收到一次事件，注销后又收到一次合成事件。
- 修复方向：捕获对应移除操作并同步解除引擎引用；单次定位监听器也应在投递完成后移除。

### 9. P2：一个计步监听器抛异常，中断同一步对其他监听器的投递

- 位置：`SensorHook.java:182`、`:195`。
- 场景：注册两个计步 listener，让遍历中的第一个抛异常。
- 实际：catch 包在整个循环外，第二个正常 listener 收不到这一步。
- 复现：`listener_exception`；健康 listener 的事件数为 0。测试通过实际 IdentityHashMap 顺序选择第一个抛错者，不依赖随机迭代顺序。
- 修复方向：按 listener 隔离异常；构建事件的失败与单个 listener 的失败分别处理。

### 10. P2：暂停时定位数据仍报告运行速度

- 位置：`MotionEngine.java:99` 附近的 `speedNow()`、`:200`；`SDKLocationHook.java` 的 getSpeed 分支。
- 场景：`mode=2`，配置速度 4.8m/s。
- 实际：位置冻结、步数不增长，但 `current().getSpeed()` 仍返回 4.8；SDK getter 也直接使用同一配置速度。
- 复现：`paused_speed`。
- 修复方向：区分配置速度与当前运动速度，暂停态返回 0。

### 11. P2：没有路线仍累计距离与步数

- 位置：`MotionEngine.java:165`、`:456`、`:504`。
- 场景：新进程没有有效路线，下发 `mode=1`，推进约一秒。
- 实际：`isActive()` 是 false，但 `isRunningNow()` 只检查模式；tick 因此仍累计约 4.82 米和 3 步。
- 复现：`run_without_route`。
- 修复方向：推进条件包含有效路线；拒绝无路线开始，或明确支持并实现独立的仅计步模式。

### 12. P2：GNSS 12 参数构造的参数顺序与单位错误

- 位置：`GnssHook.java:174` 至 `:181`。
- 官方签名的首两个参数是 `constellationType, svid`，代码却传入 `svid, CONSTELLATION_GPS`。
- 官方第十个参数是以 Hz 为单位的 `carrierFrequency`，代码传入 `cn0 - 2`；第十二个参数是 `basebandCn0DbHz`，代码传入 `1575.42`。
- 复现：`gnss_payload`；第 2 颗卫星的实际调用参数为：`constellation=2, svid=1, carrierHz=27, basebandCn0=1575.42`。
- 该测试仅记录实际传参，不复制模块构造逻辑，也不模拟 OEM 对错误参数的容错。输入本身已与 Android 公共 API 合同不符；不推断目标应用一定因此报警。
- 本地 `javap` 已核对 12 参数类型签名；参数名称、顺序与单位另由官方 API 文档核对。
- 修复方向：按真实参数语义传值，GPS L1 载频应使用 Hz 数量级，星座类型与卫星编号各就其位。

### 13. P1：任意 Dialog.dismiss 都能解除当前冻结

- 位置：`ResourceProbe.java:57` 至 `:63`。
- 场景：已经进入人脸请求冻结，另一个无关 Dialog 被 dismiss。
- 实际：hook 只检查全局 `faceFrozen()`，不检查关闭的是哪个 Dialog，立即执行 `resumeAfterFace()`。
- 复现：`unrelated_dialog_dismiss`；一个新建的无关 Dialog 的关闭回调使冻结失效。
- 修复方向：将冻结原因绑定到对应界面/请求的生命周期，不能由任意弹窗的关闭来恢复。

### 14. P2：日志限流同时跳过冻结判断

- 位置：`ResourceProbe.java:152`、`:156`、`:160`。
- 场景：上次记录文本距今不足 300ms，此时上报符合现有检测条件的“请进行人脸识别”。
- 实际：函数在冻结判断之前 return，导致该请求没有冻结。
- 复现：`log_throttle_skips_freeze`；将日志时刻设为当前后调用真实 report 方法，`faceFrozen()` 仍为 false。
- 修复方向：行为判断与日志输出分开，日志限流不能跳过状态处理。

## 关于原来的五万步异常

上一轮双源补丁的事件隔离回归仍通过；本轮另外确认存在可产生巨量步数的 Infinity 配置路径。两者都不能替代原场次的设备日志证据。当前没有原场次异常步频、硬件原始累计值或应用内部步数更新调用链，因此本报告不声称已确定原问题的唯一触发原因，也不声称 1.0.116 已经实机彻底修复。
