### 与审计报告不一致 / 需要修正的地方

审计的 14 条结论在独立核实后全部成立，但有三处细节需要修正，本轮已同步：

1. **审计替身对定位重载的覆盖被高估**。旧夹具的 `XposedHelpers.findAndHookMethod` 用
   `putIfAbsent` 按「类名.方法名」登记，因此 `requestLocationUpdates` 只保留了第一个
   四参重载，五参（带 Looper）重载从未被执行。新夹具按签名登记同名重载，与真实
   `XposedBridge.hookAllMethods` 行为一致；结论本身不变（缺的是移除路径，不是注册路径）。
2. **`Handler` 替身从不执行延迟任务**，所以「3 分钟冻结超时」此前只能通过直接调用
   `resumeAfterFace()` 间接验证，超时任务本身（含 `removeCallbacksAndMessages`）没有回归。
   新夹具用虚拟时钟 `advance(ms)` 覆盖，并由此确认了「结束命令后定时任务仍在」的问题。
3. **「五万步」与 Infinity 路径的关系**：Infinity 配置是确定可产生巨量步数的**另一条**
   路径，本轮没有任何证据表明用户原场次使用过该配置。原场次仍需设备侧日志才能定位，
   本轮不声称已定位，也不改口此前「双源计步」的因果描述。

- **可见行为变化**（都属于修缺陷带来的语义变化，需要用户知晓）：
  1. 路线跑到末端后**沿原路折返**，不再瞬移回第一段；
  2. 只有起点没有途经点时，位置固定在起点且**里程/步数不再增长**（与 README FAQ 一致）；
  3. 暂停期间 `Location.getSpeed()` 为 0，运行中仍等于配置速度；
  4. 不带 `mokr_origin`/`mokr_route` 的下发**不再清空**已有路线；空串仍然表示清空；
  5. `cfg` 里 `acc=-1` 现在真正生效（保留真实 `getGpsAccuracyStatus`），此前被忽略；
  6. 非法/超范围参数（含 `Infinity`、`NaN`）会被拒绝并保留上一份有效配置，设置页给出区间提示。
- **回滚**：`git checkout v1.0.116 的构建` 或直接安装 1.0.116 的 APK；本轮所有改动都是
  代码级、无数据迁移、无新增权限，回滚不需要清数据。

## 7. 尚未解决 / 尚未验证

1. **实机验证全部未做**（本轮无设备操作授权）：
   - 三分钟时点复测（需要同时记录引擎步数、`step register suppressed`、合成事件、
     若有排队事件则 `real step blocked type=19 value=...`）；
   - 目标应用是否真的存在 `getIntent()` 未更新的场景（取决于它自身是否调用 `setIntent`）；
   - 人脸弹窗是否走 `android.app.Dialog`（`iOSTwoButtonDialog` 系）还是纯自绘 View；
     若是自绘 View，本轮「绑定宿主弹窗」仍然成立但不会触发 dismiss，恢复依赖 3 分钟超时；
   - OEM 上 12 参 `addSatellite` 的实际可接受区间，以及目标应用是否真的读 `GnssStatus`。
2. **`addSatellite` arity > 12 的兜底分支**（例如 API 37 的 18 参重载）未在实机验证，
   代码中已标注。
3. **真实 `org.json` 与畸形 JSON**：测试替身只解析合法数字坐标，不覆盖畸形输入。
4. **原始「五万步」场次的根因**：仍缺该场次的设备日志、硬件原始累计值与目标应用内部
   计步更新链路；本轮确认的 Infinity 路径与双源计步都不能替代那份证据。
5. **路线末端折返是产品选择**，不是唯一正解。若产品要「闭环」语义，只需在
   `applyOriginRoute` 追加末点→起点一段，`advanceAlongRoute` 不用改；若要「末端停止」，
   需要同时决定里程是否继续累加（否则会回到位置与里程不同源的老问题）。
