### 与审计报告不一致 / 需要修正的地方

审计的 14 条结论在独立核实后全部成立，但有三处细节需要修正，本轮已同步：

1. **审计替身对定位重载的覆盖被高估**。旧夹具的 `XposedHelpers.findAndHookMethod` 用
   `putIfAbsent` 按「类名.方法名」登记，因此 `requestLocationUpdates` 只保留了第一个
   四参重载，五参（带 Looper）重载从未被执行。新夹具按签名登记同名重载，与真实
   `XposedBridge.hookAllMethods` 行为一致；结论本身不变（缺的是移除路径，不是注册路径）。
2. **`Handler` 替身从不执行延迟任务**，所以「3 分钟冻结超时」此前只能通过直接调用
   `resumeAfterFace()` 间接验证，超时任务本身（含 `removeCallbacksAndMessages`）没有回归。
   新夹具用虚拟时钟 `advance(ms)` 覆盖，并由此确认了「结束命令后定时任务仍在」的问题。
3. **「五万步」与 Infinity 路径的关系**：Infinity 配置是确定可产生巨量步数的**另一条**
   路径，本轮没有任何证据表明用户原场次使用过该配置。原场次仍需设备侧日志才能定位，
   本轮不声称已定位，也不改口此前「双源计步」的因果描述。

  1. 路线跑到末端后**沿原路折返**，不再瞬移回第一段；
  2. 只有起点没有途经点时，位置固定在起点且**里程/步数不再增长**（与 README FAQ 一致）；

  无数据迁移、无新增权限，回滚不需要清数据。

### 7.2 已知限制（非本轮修复范围）

1. **`addSatellite` arity > 12 的兜底分支**（例如 API 37 的 18 参重载）未实机验证，代码中已标注。
2. **真实 `org.json` 与畸形 JSON**：测试替身只解析合法数字坐标，不覆盖畸形输入。
3. **原始「五万步」场次的根因**：仍缺该场次的设备日志、硬件原始累计值与目标应用内部
   计步更新链路；本轮确认的 Infinity 路径与双源计步都不能替代那份证据。
4. **系统回调拦截只覆盖 `LocationListener` 形态**；`PendingIntent` 与
   `BatchedLocationCallback` 两种形态本来就不接收合成流，也不在拦截范围内。
5. **路线末端折返是产品选择**，不是唯一正解。若产品要「闭环」语义，只需在
   `applyOriginRoute` 追加末点→起点一段，`advanceAlongRoute` 不用改；若要「末端停止」，
   需要同时决定里程是否继续累加（否则会回到位置与里程不同源的老问题）。
6. 候选列表里 Android 10 的旧类名在 API 36 上必然不存在，日志会出现一行
   `callback guard not found on ...ListenerTransport`，属预期噪声，不是失败。

### A5 的类名/签名以 AOSP 源码逐版本核对

| 版本 | 载体类 | 方法签名 |
|---|---|---|

### A6（第三轮，C1，P1）：完成确认的反射调用被访问检查拒绝

第三轮验收结论的另一处阻塞：`completeSystemCallback()` 用
`callback.getClass().getMethod("sendResult", Bundle.class)` 取方法再 `invoke`。
设备上真实回调是 `android.os.IRemoteCallback$Stub$Proxy`——方法 public，
但**实现类非 public**（第三轮验收已用设备 `framework.jar` 的 class_def 证明：
`IRemoteCallback`=public、`IRemoteCallback$Stub$Proxy`=access_flags 0x0），
因此跨包 `invoke` 抛 `IllegalAccessException`：确认没发出去，外层却已经短路了投递。

复现（本地固定夹具，与设备可见性形态一致）：`android.os` 包内的非公开内部类实现
公开接口，位于与 `LocationProbe` **不同**的包。

```
修复前：LOG MokrRun: onComplete notify skipped (java.lang.IllegalAccessException:
          class com.mokrun.app.xposed.LocationProbe cannot access a member of class
          android.os.RemoteCallbackProxyFixture$Proxy with modifiers "public")
        FAIL system_callback_suppressed_during_takeover
修复后：PASS（completed=1，attempts=1，delivered=0）
```

修法：从**公开接口**取 Method——`Class.forName("android.os.IRemoteCallback", false,
callback.getClass().getClassLoader())` 后 `getMethod("sendResult", Bundle.class)`，
再对该对象 `invoke`（接口是 public，实现类可见性不再影响调用）。解析结果缓存一次；
若接口解析失败，再退化为「在实现类的公开接口里搜 `sendResult(Bundle)`」。
无编译期依赖（未 import `IRemoteCallback`），因此不需要额外 `android.jar` 符号。

**失败处理策略**：补发失败只记 `onComplete notify failed -> <cause>`（已解包
`InvocationTargetException`）并继续短路——「接管期间不投递真实位置」优先；
系统侧可能少收一次完成回执，日志关键字固定，便于现场核对是否为该分支。

### 二次修复的设计取舍

1. **A1**：把「带配置的控制命令」和「provider 值变化」都提升为显式命令，
   与 `setMode` 走同一个取消冻结入口；provider 值**未变化**时不改变状态，
   因此「prefs 是旧值」的轮询仍然不会撤销新的结束/暂停。
2. **A2**：选择「统一时间窗」而不是「无条件补齐」：`effDt = min(dt, 2 s)` 同时用于
   距离、位置推进与步数；超过 2 秒的部分视为调度停摆不补算，任何间隔下两者都同源。
3. **A3**：注册表改为按 Sensor 实例（`==`）保存，注销精确到实例；
   应用若传入等价但不同实例的 Sensor，只有该类型只剩一条时才等价移除，
   同类型多条且不匹配时保守不动——避免「为避免误删而完全不删」导致监听器泄漏。
4. **A4**：单次定位在接管期间**短路原调用**（`setResult(null)`，方法返回 void），
   由合成流独占；连续注册**保留真实注册**（否则「结束」后拿不回真实定位），
   改为在系统回调入口丢弃真实事件（A5 修正了入口的类名与签名）。
5. **A5**：不再依赖单一隐藏类名。候选列表覆盖 Android 10 与 11~16 两代命名，
   命中后按方法名挂所有重载，避免签名差异导致静默失效；同时补发 `onComplete`，
   避免系统侧投递记账卡住。
6. **A6**：反射不按实现类取 Method。可见性由**声明类**决定，`getMethod` 返回的
   Method 仍绑定非 public 的代理类，跨包 `invoke` 会被拒绝；改从公开接口
   `android.os.IRemoteCallback` 解析，符合「不增加编译期依赖」的要求。
